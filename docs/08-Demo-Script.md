## ช่วงที่ 1 — Problem & Requirement · 2 นาที

**ปัญหา (30 วินาที)**

> ร้านอะไหล่คอมพิวเตอร์ขายของที่ต้องรับประกัน**รายชิ้น** — RAM ตัวนี้ซื้อเมื่อไร ยังอยู่ในประกันไหม
> ปัญหาคือของแบบนี้**นับเป็นจำนวนไม่ได้** ต้องติดตามทีละชิ้นด้วยหมายเลขซีเรียล
> และถ้าจ่าย S/N เดียวกันซ้ำสองครั้ง ประวัติประกันของลูกค้าจะพังทันที

**Stakeholder (20 วินาที)** — 3 กลุ่ม: ลูกค้าทั่วไป (เช็คประกันเอง ไม่ต้องโทรถาม) · พนักงานสาขา (ขายหน้าร้าน) · สำนักงานใหญ่ (คุมสต็อกรวม อนุมัติการสั่งซื้อ)

**Key FR/NFR (50 วินาที)** — **ไม่ต้องไล่ทั้ง 15 ข้อ** เลือกพูด 4 ข้อที่เป็นแกน:

| | |
|---|---|
| **FR-002/003** | สต็อกรายชิ้นมี S/N ไม่ใช่การนับจำนวน — เป็นรากของทั้งระบบ |
| **FR-004/005** | บันทึกขายแล้วคำนวณวันหมดประกันอัตโนมัติจากวันขายจริง |
| **NFR-REL-01** | **หนึ่งชิ้นขายได้ครั้งเดียว แม้มีคนกดพร้อมกัน** ← ความท้าทายหลักของโปรเจกต์ |
| **NFR-SEC-02** | สาขาเห็นได้เฉพาะข้อมูลสาขาตัวเอง บังคับที่ server ไม่ใช่ซ่อนปุ่ม |

**User Story สำคัญ (20 วินาที)**

> **US-01** — *ในฐานะเจ้าของอุปกรณ์ ฉันอยากกรอก S/N เพื่อเช็คประกัน เพื่อที่จะไม่ต้องโทรถามร้าน*

## ช่วงที่ 2 — Architecture & Engineering Evidence · 3 นาที

**Architecture (45 วินาที)** — เปิด [`03-Architecture-Design.md`](03-Architecture-Design.md) §1-§2

> ระบบเดียวแบ่งด้วย role ไม่ใช่ 3 แอปแยก (ADR-001) — เพราะทีมเล็กและข้อมูลต้อง consistent
> **จุดที่ตั้งใจออกแบบ:** ทุก route ที่ต้องล็อกอินผ่าน `deps.py` จุดเดียว
> ตรวจสิทธิ์ที่เดียว — ถ้ากระจายไปตาม router พลาดที่เดียวคือรั่ว

**Data/API (30 วินาที)** — ชี้ ER Model §6 และตาราง API §7

> 10 ตาราง · endpoint ที่เอกสารระบุ**ตรงกับ `prefix=` ในโค้ดทุกตัว** — ตรวจแล้ว

**ADR-002 — หัวใจของงาน (45 วินาที)** ⭐ *จุดที่ควรใช้เวลามากที่สุดในช่วงนี้*

> ปัญหา: ถ้าพนักงาน 2 คนกดขาย S/N เดียวกันพร้อมกัน จะเกิดอะไร
> วิธีแก้: **conditional UPDATE** `WHERE status='InStock'` แล้วเช็ค `rowcount` — ใครได้ 1 คนนั้นขายได้
> ร่วมกับ **Idempotency-Key** กันเน็ตช้าแล้วกดซ้ำ
> **พิสูจน์แล้ว: ยิง 10 thread แข่งกันจริงบน Postgres จริง สำเร็จได้แค่ 1 เสมอ** — ไม่ใช่ mock

**Git/PR (30 วินาที)** — เปิดแท็บ GitHub PR

> **18 PR · CI เขียวทุกใบก่อน merge · เปิด branch protection แล้ว push ตรงเข้า `main` ไม่ได้เลย**
> พร้อมพูดข้อจำกัดเอง: *"PR ทุกใบ reviews = 0 เพราะทำคนเดียว — ได้ branch hygiene กับ CI gate แต่ยังไม่ใช่ code review เราเขียนไว้ตรง ๆ ใน Retrospective"*

**Test / CI-CD (30 วินาที)** — เปิดแท็บ CI

> **122 tests ครบ 4 ระดับ** — unit 14 · integration 95 · acceptance 9 · concurrency 4
> acceptance test เขียนตาม Given-When-Then ของ User Story โดยตรง **AC ที่เพี้ยนจากโค้ดจะทำให้ test พัง**
> CI รัน lint + test บน Postgres จริงทุก push · deploy อัตโนมัติเมื่อ merge

### B. Edge case — เลือก 1 ใน 2 (1.5 นาที)

**ตัวเลือกที่ 1 — แยกหน้าที่ (แนะนำ ทำเร็ว เห็นผลชัด)**

> กลับไปที่บัญชี `admin` แล้วชี้ว่า **ไม่มีเมนู "บันทึกขาย"**
> *"Admin อนุมัติคำขอสั่งซื้อได้ แต่ขายเองไม่ได้ — คนอนุมัติกับคนขายต้องแยกกัน
> และไม่ได้แค่ซ่อนปุ่ม ถ้ายิง API ตรงก็ได้ 403 มี test คุมไว้"*

**ตัวเลือกที่ 2 — ข้อความ error ที่ช่วยผู้ใช้**

> หน้าสาธารณะ → พิมพ์ `SN-0001234` (ผิดรูปแบบ) → กดตรวจสอบ
> *"เดิมบอกแค่ 'ไม่พบข้อมูล' ซึ่งเป็นทางตัน — เราเจอตอนเดิน task ตาม NFR-USE-01
> ตอนนี้บอกรูปแบบที่ถูกต้องและบอกทางออกให้"*

> 💡 **ถ้าเน็ตหรือ Render มีปัญหา** — สลับไปพูดช่วงที่ 4 ก่อน แล้วกลับมาทำ demo ทีหลัง

## ช่วงที่ 4 — AI Usage Disclosure · 1 นาที

**AI ช่วยอะไร (15 วินาที)**

> ใช้ AI แทบทุกขั้น — requirements, architecture, code, test, เอกสาร, debug, สร้างข้อมูลตัวอย่าง
> บันทึกไว้ **46 entry** พร้อม 7 คอลัมน์ที่เกณฑ์กำหนด

**ทีมตรวจอย่างไร (20 วินาที)**

> หลักที่ใช้ตลอด: **รันจริงแล้ววัดผล ไม่ใช่อ่านโค้ดซ้ำ**
> บั๊กร้ายแรงทุกตัวถูกจับได้ด้วยวิธีนี้ ไม่ใช่ด้วยการรีวิวด้วยตา

**สิ่งที่ reject จาก AI (25 วินาที)** ⭐ *เกณฑ์ให้คะแนนตรงนี้ เลือกพูด 2 ตัวอย่าง*

> **1.** AI ตีความ "Hardware" ว่าเป็นเครื่องมือช่าง แล้วออกแบบ data model แบบนับจำนวน —
> ทีมปฏิเสธและให้ทำใหม่เป็น serialized inventory ซึ่งใช้ตลอดโครงงาน
>
> **2.** AI เขียน test กัน N+1 query แล้วบอกว่าผ่าน — เราเอา test ไปรันกับโค้ดเก่าที่ยังมีบั๊ก
> เพื่อดูว่ามัน fail จริงไหม **แล้วพบว่ามันไม่ fail** เพราะดักฟัง database engine ผิดตัว
> **test ที่ผ่านโดยไม่มีทาง fail = test ที่ไม่ได้ทดสอบอะไรเลย**
>
> บันทึกความผิดพลาดของ AI ไว้ **7 ข้อ** ในเอกสาร ไม่ได้เขียนแต่ด้านที่ดี

## ช่วงที่ 5 — Retrospective · 2 นาที

**สิ่งที่สำเร็จ (30 วินาที)**

> แก้ความเข้าใจผิดเรื่อง requirement ได้**ก่อน**เขียนโค้ด · concurrency พิสูจน์ได้ด้วย test จริง · deploy ขึ้น production จริง

**ปัญหาจริง (40 วินาที)**

> ประเมิน timeline ผิด 3 รอบ · scope ขยายผ่าน CR 15 ครั้ง สะท้อนว่า elicitation แรกไม่ครอบคลุมพอ
> · **ใช้ branch/PR ช้าเกินไป — 38 commit แรก push ตรงเข้า `main`**

**บทเรียนที่ใหญ่ที่สุด (30 วินาที)** ⭐

> **บั๊กที่อันตรายที่สุดคือบั๊กที่ไม่ทำให้อะไรพัง** — จัดกลุ่มเวลาด้วย UTC จนยอดขายไปอยู่ผิดวัน
> แต่กราฟยังดูปกติ · test ที่ fail ไม่ได้ · เครื่องมือวัดที่รายงานผ่านหมด
> ทุกตัวเจอเพราะรันจริง ไม่ใช่เพราะอ่านโค้ด

**Technical Debt ที่ยอมรับ (20 วินาที)** — พูดเองก่อนถูกถาม

> 1. **NFR-USE-01 ยังไม่มีหลักฐานจากผู้ใช้จริง** — วัดส่วนที่เครื่องวัดได้แล้ว 10/10 แต่ตัวเลข
>    "90% ใน 60 วินาที" ต้องมาจากคนจริง เราเลือกเขียนว่ายังไม่ได้ทำ แทนที่จะกรอกตัวเลขเอง
> 2. **PR ยังไม่มีผู้รีวิวคนที่สอง**
> 3. อีเมลแจ้งเตือนบน production ยังเป็น dev-mode เพราะ credential ต้องตั้งโดยทีมเท่านั้น

## 🎯 คำถามที่น่าจะโดนถาม + คำตอบ

| คำถาม | ตอบ |
|---|---|
| **"ทำไมไม่ใช้ transaction ธรรมดา?"** | ใช้ transaction อย่างเดียวไม่พอเพราะ read-then-write ยังมีช่องว่าง · conditional UPDATE ทำให้การเช็คกับการเขียนเป็น atomic ในคำสั่งเดียว · ส่วน Idempotency-Key แก้คนละปัญหา คือ retry จากเน็ตช้า |
| **"ทดสอบ concurrency ยังไง"** | 10 thread ยิง `POST /api/sales` พร้อมกันบน Postgres จริง assert ว่าสำเร็จ 1 ที่เหลือได้ 409 — ดู `tests/concurrency/` |
| **"ใช้ AI เยอะขนาดนี้ รู้ได้ไงว่าถูก"** | ไม่เชื่อเพราะอ่านแล้วดูดี แต่เพราะรันแล้ววัด · ตัวอย่างชัดที่สุดคือเอา test ใหม่ไปรันกับโค้ดที่ยังผิด ถ้าไม่ fail แปลว่า test นั้นใช้ไม่ได้ — เจอมาแล้ว 2 ครั้ง |
| **"ทำไม usability test ไม่ทำ"** | ทำส่วนที่วัดด้วยเครื่องมือได้แล้ว 10/10 แต่ตัวเลข "90% ใน 60 วินาที" ต้องมาจากผู้ใช้จริงที่ไม่ใช่คนทำระบบ · เราเลือกบันทึกว่าเป็นช่องว่าง แทนที่จะกรอกตัวเลขที่ไม่มีที่มา |
| **"ถ้าจะขยายเป็น 50 สาขาต้องแก้อะไร"** | ต้องทำ pagination แทนเพดาน 200 แถว (บันทึกเป็น K-07) · dashboard ใช้ aggregate ใน SQL อยู่แล้วจึงไม่ใช่คอขวด · และควรทำ background job แทน manual purge |
| **"ทำไมไม่มี unit test เยอะกว่านี้"** | ตรรกะส่วนใหญ่อยู่ที่ขอบเขตของ DB (การขายซ้ำ, scope สาขา) ซึ่ง mock แล้วจะไม่ได้ทดสอบสิ่งที่อยากทดสอบ · unit test จึงเจาะเฉพาะฟังก์ชันบริสุทธิ์ 14 เคส ที่เหลือทดสอบกับ Postgres จริง |
