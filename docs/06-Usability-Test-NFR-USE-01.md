# NFR-USE-01 — Usability Test

> **เกณฑ์ที่ต้องพิสูจน์ (จาก [01-Requirements-Package.md](01-Requirements-Package.md)):**
> ผู้ใช้ใหม่ต้องทำ task ค้นหา/เช็คประกันสำเร็จ **≥ 90% ภายใน 60 วินาที โดยไม่ต้องมีคนสอน**
> · วิธีวัด: Task-based user test

---

## ⚠️ ขอบเขตของเอกสารนี้ — อ่านก่อน

เอกสารนี้แบ่งเป็น **2 ส่วนที่ห้ามสับสนกัน**

| ส่วน | ใครทำได้ | สถานะ |
|---|---|---|
| **ส่วน A** — สิ่งที่วัดได้โดยไม่ต้องมีผู้ใช้ (จำนวนขั้นตอน, heuristic evaluation, การเข้าถึงด้วยคีย์บอร์ด/โปรแกรมอ่านหน้าจอ, มือถือ) | ผู้พัฒนา/AI วัดได้ | ✅ ทำแล้ว — พบและแก้ข้อบกพร่อง **4 จุด** (D-01 ถึง D-04) |
| **ส่วน B** — ทดสอบกับผู้ใช้จริง | ต้องมีผู้ใช้จริงที่ไม่ใช่คนทำระบบ | ✅ **ทำแล้ว 2026-08-25 — ผู้ใช้ภายนอก 4 คน สำเร็จ 4/4 เฉลี่ย 22.0 วินาที** · ตัดผู้พัฒนาออกจากกลุ่มตัวอย่าง · n=4 ยังไม่พอยืนยัน ≥90% เชิงสถิติ (ดู §B3) |

**ส่วน A ไม่ใช่ตัวแทนของส่วน B** — heuristic evaluation บอกได้ว่า "ตรงไหนน่าจะมีปัญหา" แต่บอกไม่ได้ว่า
"ผู้ใช้จริง 9 ใน 10 คนทำสำเร็จใน 60 วินาทีหรือไม่" ซึ่งเป็นสิ่งที่ NFR ข้อนี้ระบุไว้ตรง ๆ

ข้อมูลในส่วน B เป็นข้อมูลเชิงประจักษ์ **AI สร้างขึ้นเองไม่ได้อย่างซื่อสัตย์**
(บันทึกไว้ตั้งแต่ [02-AI-Usage-Log.md](02-AI-Usage-Log.md) entry #26 · AI ปฏิเสธการกรอกตัวเลขแทน 2 ครั้ง)
**ตัวเลขใน §B3 มาจากผู้ใช้จริงที่ทีมไปทดสอบเองเมื่อ 2026-08-25** ไม่ใช่ AI สร้างขึ้น

# ส่วน A — ผลที่วัดแล้ว (ไม่ต้องใช้ผู้ใช้)

## A1. เดิน task ตามเส้นทางจริงบน production

ทดสอบบน `https://sme-inventory-frontend.onrender.com` (2026-08-24)

| สิ่งที่วัด | ผล |
|---|---|
| องค์ประกอบที่กดได้บนหน้า | **2 ชิ้น** (ช่องกรอก + ปุ่ม) — ไม่มีสิ่งรบกวน |
| ขั้นตอนขั้นต่ำถึงผลลัพธ์ | **2 ขั้น** (พิมพ์ S/N → กดตรวจสอบ) |
| ต้องล็อกอินก่อนไหม | ไม่ต้อง |
| เวลาตอบกลับ (Render free tier, เครื่องตื่นแล้ว) | ~3 วินาที |
| ผลลัพธ์ที่แสดง | รุ่นสินค้า · สถานะประกัน · วันหมดประกัน (พ.ศ.) |

**สรุป A1:** โครงสร้าง task สั้นมาก (2 ขั้น) ซึ่งเอื้อต่อเป้าหมาย 60 วินาทีอย่างมาก
ข้อจำกัดหลักที่เหลือจึงไม่ใช่จำนวนขั้นตอน แต่คือ **ผู้ใช้จะรู้ไหมว่าต้องพิมพ์อะไร**

## A2. ข้อบกพร่องที่พบจากการเดิน task — และแก้แล้ว

### 🔴 D-02 ข้อความ error เป็นทางตัน (แก้แล้ว)

| | |
|---|---|
| **เดิม** | "ไม่พบข้อมูล กรุณาตรวจสอบ S/N อีกครั้ง" |
| **ปัญหา** | ไม่บอกว่ารูปแบบที่ถูกต้องคืออะไร ผู้ใช้ที่พิมพ์ผิดรูปแบบจึงลองใหม่แบบเดิมซ้ำ ๆ |
| **รวมกับ D-01** | ผู้ใช้ทำตามตัวอย่าง → ผิด → error ไม่บอกทางออก → **ตันสนิท** ภายในไม่กี่วินาทีแรก |
| **แก้เป็น** | บอกรูปแบบที่ถูกต้องพร้อมตัวอย่างจริง + บอกกรณีที่ของยังไม่ถูกบันทึกขาย ให้ติดต่อสาขา |

> D-01 + D-02 รวมกันคือความเสี่ยงที่ตรงกับเกณฑ์ NFR มากที่สุด เพราะโจมตีเงื่อนไข
> **"โดยไม่ต้องมีคนสอน"** โดยตรง — ทั้งสองข้อแก้ก่อนรัน test กับผู้ใช้จริงแล้ว
> เพื่อไม่ให้ผลการทดสอบสะท้อนบั๊กที่รู้อยู่แล้วว่าต้องแก้

## A3. Heuristic evaluation (Nielsen 10) — เฉพาะหน้าเช็คประกัน

| # | Heuristic | ผล | หมายเหตุ |
|---|---|---|---|
| 1 | Visibility of system status | ✅ | ปุ่มเปลี่ยนเป็น "กำลังตรวจสอบ..." ระหว่างรอ |
| 2 | Match with real world | ✅ | ใช้คำว่า "หมายเลขซีเรียล (S/N)" + ระบุว่าหาได้จากสติกเกอร์/กล่อง · วันที่เป็น พ.ศ. |
| 3 | User control & freedom | ✅ | แก้ค่าแล้วค้นใหม่ได้ทันที ไม่มี state ค้าง |
| 4 | Consistency & standards | ✅ | ใช้ `.rd-*` ชุดเดียวกับทั้งระบบ |
| 5 | Error prevention | 🟡 | ยังไม่มี input mask/validate รูปแบบก่อนยิง API — ปล่อยให้ยิงแล้วค่อยบอกว่าไม่พบ |
| 6 | Recognition over recall | ✅ | ตัวอย่างรูปแบบอยู่ในช่องกรอก ไม่ต้องจำเอง (หลังแก้ D-01) |
| 7 | Flexibility & efficiency | ✅ | กด Enter ส่งฟอร์มได้ ไม่ต้องเอื้อมไปกดปุ่ม |
| 8 | Aesthetic & minimalist | ✅ | ทั้งหน้ามีองค์ประกอบกดได้ 2 ชิ้น |
| 9 | Help users recover from errors | ✅ | หลังแก้ D-02 — ก่อนหน้านี้ **ไม่ผ่าน** |
| 10 | Help & documentation | 🟡 | ไม่มีลิงก์ช่วยเหลือ/ตัวอย่างภาพว่าสติกเกอร์ S/N อยู่ตรงไหนของสินค้า |

**เหลือเป็นข้อเสนอ (ยังไม่ทำ):** #5 validate รูปแบบก่อนยิง API, #10 ใส่ภาพประกอบว่า S/N อยู่ตรงไหน
— ตั้งใจรอผลจากผู้ใช้จริงก่อนว่าจำเป็นจริงไหม **และผลออกมาแล้วใน §B3: ไม่มีใครทำไม่สำเร็จ
และไม่มีปัญหาใดพบซ้ำตั้งแต่ 2 คน** จึงยังไม่แก้ทั้งสองข้อ — เป็นการตัดสินใจจากข้อมูล ไม่ใช่การละเลย

# ส่วน B — สคริปต์ทดสอบกับผู้ใช้จริง (ทีมต้องรันเอง)

## B1. เตรียมตัว

- **ผู้เข้าร่วม:** 5–8 คน ที่**ไม่ใช่คนทำระบบ** และไม่เคยเห็นระบบนี้มาก่อน
  (5 คนเพียงพอจะเจอปัญหาส่วนใหญ่ แต่ต้องอย่างน้อย **10 คนจึงจะอ้าง "90%" ได้อย่างมีความหมาย** —
  ถ้าได้ไม่ถึง 10 ให้รายงานเป็น "x/n คน" ตรง ๆ อย่าแปลงเป็นเปอร์เซ็นต์ให้ดูดี)
- **อุปกรณ์:** เครื่องของผู้เข้าร่วมเอง เปิด `https://sme-inventory-frontend.onrender.com`
- **สิ่งที่ต้องเตรียม:** S/N จริง 1 หมายเลขที่ขายแล้ว (ดูได้จากหน้าบันทึกขาย หรือถามผู้ดูแลระบบ)
- **จับเวลา:** เริ่มจับตอนพูดโจทย์จบ หยุดเมื่อผู้ใช้บอกคำตอบได้

## B2. บทพูด (อ่านตามนี้ ห้ามเพิ่มคำใบ้)

> "สมมติคุณซื้อการ์ดจอมาจากร้านนี้ แล้วอยากรู้ว่ายังอยู่ในประกันอยู่ไหม
> นี่คือหมายเลขซีเรียลบนตัวสินค้า: `____________`
> ช่วยหาคำตอบจากเว็บนี้ให้หน่อยครับ/ค่ะ — ระหว่างทำ ถ้าคิดอะไรอยู่พูดออกมาดัง ๆ ได้เลย"

**ถ้าผู้ใช้ถามคำถาม ให้ตอบว่า "ลองดูตามที่คิดได้เลยครับ/ค่ะ" เท่านั้น** — ห้ามชี้ทาง
เพราะเกณฑ์ระบุว่า "โดยไม่ต้องมีคนสอน" ถ้าสอนแล้วผลที่ได้จะไม่ตรงกับสิ่งที่ NFR ถาม

## B3. ผลการทดสอบจริง (2026-08-25)

**ผู้ใช้ภายนอก 4 คน** — นักศึกษาที่ไม่ใช่ทีมพัฒนา ไม่เคยเห็นระบบมาก่อน · ทดสอบทีละคน ไม่ให้ดูกัน
· แต่ละคนได้ S/N คนละหมายเลขและคนละหมวดสินค้า (GPU/Mainboard/CPU) เพื่อไม่ให้จำจากคนก่อนหน้าได้
  และได้ทดสอบไปด้วยว่าระบบตอบถูกทุกหมวด ไม่ใช่ถูกแค่บางประเภท
· กติกาที่แจ้งผู้ดำเนินการก่อนเริ่ม: อ่านบทพูดตาม §B2 · ไม่ชี้ทาง · จับเวลาตั้งแต่พูดโจทย์จบ
  ถึงตอนผู้เข้าร่วมบอกคำตอบ · **บันทึกจุดที่ลังเลแม้ทำสำเร็จ**

### ⚠️ ข้อจำกัดที่ต้องระบุให้ชัด — ผลนี้ยังไม่ยืนยันเกณฑ์ ≥90%

ผลที่สังเกตได้คือ 4/4 ซึ่ง**สูงกว่าเป้าหมาย 90%** แต่ **n=4 เล็กเกินกว่าจะสรุปเชิงสถิติได้**

ตาม **rule of three** — เมื่อไม่พบความล้มเหลวเลยใน n ครั้ง ขอบบนของอัตราล้มเหลวจริงที่ระดับ
ความเชื่อมั่น 95% ประมาณ `3/n` · กรณีนี้ `3/4 = 75%` แปลว่า **อัตราสำเร็จจริงอาจต่ำถึง ~25%
ได้โดยไม่ขัดกับผลที่เราเห็น** · การจะยืนยัน ≥90% อย่างมีนัยสำคัญต้องใช้ผู้เข้าร่วม **ราว 30 คน**

> การตัดผู้พัฒนาออกทำให้ขอบบนนี้**แย่ลงจาก 60% เป็น 75%** — เป็นราคาที่ต้องจ่ายและระบุไว้ตรง ๆ
> ตัวเลขที่ซื่อสัตย์แต่ดูแย่กว่า ดีกว่าตัวเลขที่สวยแต่มีคนทำระบบปนอยู่ในกลุ่มตัวอย่าง

**จึงรายงานเป็น "4/4 คน" ไม่ใช่ "100%"** — และไม่เคลมว่า NFR-USE-01 ผ่านเกณฑ์เชิงสถิติแล้ว
สิ่งที่พูดได้อย่างซื่อสัตย์คือ: *ทดสอบกับผู้ใช้ภายนอกแล้ว ทุกคนทำสำเร็จภายในครึ่งหนึ่งของเวลา
ที่กำหนด และไม่พบอุปสรรคที่ทำให้ใครทำไม่สำเร็จ*
