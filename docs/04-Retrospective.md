## 1. สิ่งที่สำเร็จ (What Went Well)

**1.1 แก้ความเข้าใจผิดเรื่อง requirement ได้ตั้งแต่ต้น ก่อนลงมือเขียนโค้ดจริง**
ร่างแรกของ Data Model สมมติว่า "Hardware" หมายถึงเครื่องมือช่าง (เช่น ไขควง) ทั้งที่ context จริงของร้านคือ RAM/CPU/Mainboard ทีมจับได้ตั้งแต่ขั้น Requirement (ก่อนมี repo ด้วยซ้ำ) และสั่งให้ AI **ทำ Data Model ใหม่ทั้งหมด** เป็นแบบ serialized inventory (รายชิ้นมี S/N) — ผลคือ Data Model ที่ใช้จริงตลอดโครงงานถูกต้องตั้งแต่ต้น ไม่ต้อง migrate โครงสร้างใหญ่กลางทาง (ดู `docs/02-AI-Usage-Log.md` entry #3)

**1.2 Concurrency control (ADR-002) พิสูจน์ได้จริง ไม่ใช่แค่ทฤษฎี**
NFR-REL-01 (กันขายสินค้าชิ้นเดียวซ้ำ) เป็นความท้าทายหลักของโปรเจกต์ ทดสอบด้วย concurrency test ที่ยิง 10 thread แข่งกันขายจริงบน Postgres จริง (ไม่ใช่ mock) ยืนยันว่ามีแค่ 1 thread สำเร็จเสมอ — pattern เดียวกัน (conditional UPDATE + idempotency key) ถูกนำไปใช้ซ้ำกับ PR approve/reject ได้โดยตรงในสัปดาห์ 3

**1.3 Deploy จริง ไม่ใช่แค่ "รันได้บนเครื่อง"**
ระบบ live จริงบน Render (frontend + backend + Postgres) หลัง debug deploy failure 3 รอบจริง (Python version, bare `alembic` command) แต่ละรอบ verify ด้วย log จริงจาก Render CLI ไม่ใช่เดา — จุดที่ภูมิใจที่สุดคือรอบที่ 3 (bare `alembic` bug) ที่ **reproduce บั๊กเดิมบนเครื่อง local ได้ก่อนแก้** แทนที่จะเดาแล้วลอง push ใหม่ไปเรื่อย ๆ

**1.4 Test coverage ครอบคลุมหลายมิติจริง**
113 automated tests ครอบคลุม unit/integration/concurrency/security ไม่ใช่แค่ happy path — รวม STRIDE mitigation verification (5 tests), NFR-PRIV-01 purge (5 tests), และ load test แยกต่างหากสำหรับ NFR-PERF-01 ที่วัดผลจริงด้วย 200 concurrent request

**1.5 AI Usage Log ที่ซื่อสัตย์จริง ไม่ใช่แค่ list ว่า "ใช้ AI ทำอะไรบ้าง"**
มี entry ที่บันทึกความผิดพลาดของ AI ตรง ๆ อย่างน้อย 4 ครั้ง (สมมติผิดเรื่อง Hardware, เดาสาเหตุ deploy fail ผิดในรอบแรก, ทำ dependency ของ tooling พังชั่วคราว, บั๊ก debounce/seed script) — ตรงกับหลักที่ Deck 05 ต้องการ คือมีหลักฐานว่าทีม/AI **reject หรือแก้ output ที่ผิด** ไม่ใช่แค่ยอมรับทุกอย่างที่ AI สร้าง

## 2. ปัญหาจริงที่เจอระหว่างทาง (Real Problems)

**2.1 ประเมิน timeline ผิดถึง 3 รอบ**
เริ่มจากเข้าใจว่าเหลือเวลา 1 สัปดาห์ → แก้เป็น 4 สัปดาห์ → แก้เป็น 8 สัปดาห์ ทุกครั้งต้องย้อนกลับไปปรับ priority ของ FR/NFR ใหม่ทั้งชุด (CR-003, CR-004, CR-005) — เสียเวลาที่ไม่จำเป็นและทำให้ RTM/priority ต้องแก้ซ้ำหลายรอบ บทเรียนคือควรยืนยันกรอบเวลาที่แน่นอนกับผู้สอน/สมาชิกทีมให้ชัดตั้งแต่ประชุมแรก ก่อนเริ่ม Requirement Package

**2.2 Requirement ใหม่โผล่มากลางทางหลายรอบ**
CR-001/CR-002 (data retention, reorder point ต่อสาขา) และ CR-006 ถึง CR-013 (email alert, รูปสินค้า, KPI dashboard, ขยาย seed data, ธีมใหม่, จัดการสินค้าให้ครบ, ขยายเป็น 4 สาขา, รื้อ Dashboard ใหม่) ล้วนเป็นสิ่งที่ไม่มีในร่างแรก ต้องเพิ่มระหว่างทาง — ถึงจะมี Change Request log กำกับไว้ครบ แต่การที่ scope ขยายบ่อยขนาดนี้สะท้อนว่าขั้น elicitation แรกยังไม่ครอบคลุมพอ

**2.3 บั๊กที่เกิดจากสภาพแวดล้อม Windows หลายจุด**
พบปัญหา encoding ซ้ำ ๆ กันหลายครั้งในบริบทต่างกัน: `print()` ข้อความไทยพังตอนรัน seed script (cp1252 default), `pip install -r requirements.txt` อ่านไฟล์ที่มี comment ภาษาไทยไม่ได้ด้วยเหตุผลเดียวกัน — เป็น class of bug เดียวกันที่เกิดซ้ำเพราะไม่มีใครตั้ง `PYTHONUTF8=1` เป็นค่า default ของ environment ตั้งแต่ต้น

**2.4 บั๊ก logic จริงที่จับได้จากการทดสอบ ไม่ใช่จากการอ่านโค้ด**
สองบั๊กที่สำคัญที่สุด: (ก) debounce ของ email alert ยิงซ้ำผิดจังหวะเพราะ endpoint รับสต็อกกับ endpoint ขายเรียก logic เดียวกันแบบ symmetric ทั้งที่ควรมีแค่ฝั่งขายที่ยิง alert ใหม่ได้ (ข) seed script คำนวณ scenario สต็อกผิดเพราะใช้ตัวแปรที่เพิ่มค่าไม่คงที่เป็นตัวหาร modulo ทำให้วนซ้ำ pattern เดิม — ทั้งสองจับได้จาก **assertion จริงที่ fail** และการเปิดดู UI จริง ไม่ใช่จากการอ่าน code review เฉย ๆ ยืนยันว่าวินัย "รันจริงก่อนถือว่าเสร็จ" ที่ตั้งไว้ทั้งโครงงานมีประโยชน์จริง

**2.5 เกือบทำ tooling environment ของตัวเองพังระหว่าง hardening**
ระหว่างอัปเกรด dependency สำหรับแก้ CVE ระบุ Python environment ผิด ติดตั้ง package ของโปรเจกต์ทับลงใน environment ที่เครื่องมือ (Claude Code) ใช้งานอยู่จริง ทำให้ downgrade package ที่ระบบอื่นต้องพึ่งพา — จับได้จาก error message ของ pip เองและแก้ก่อนเกิดความเสียหายถาวร บทเรียนสำคัญ: **โปรเจกต์นี้ไม่เคยมี isolated venv ของตัวเองเลยตลอดทั้งโครงงานจนถึงจุดนี้** ทั้งที่ README แนะนำให้สร้างไว้ตั้งแต่ต้น

**2.6 ใช้ Git branch/PR workflow ช้าเกินไป — 38 commit แรกไม่ผ่าน branch เลย**

ตัวเลขจริง: **38 commit แรก push ตรงเข้า `main`** ไม่ผ่าน branch เลย ·
เปลี่ยนมาใช้ feature branch + Pull Request ตั้งแต่ **commit ที่ 39 เป็นต้นไป และทุก commit หลังจากนั้นผ่าน PR ทั้งหมด**
เริ่มจาก [#1](https://github.com/kit-sinlapasa/sme-inventory-system/pull/1) (usability test) และ [#2](https://github.com/kit-sinlapasa/sme-inventory-system/pull/2) (แก้ N+1)
โดยแต่ละใบทิ้ง merge commit ที่อ้างอิงกลับไปหา PR ได้จาก `git log`

> เขียนเป็น "38 commit แรก" ไม่ใช่ "38 จาก 42" โดยตั้งใจ — ยอดรวมและจำนวน PR
> ขยับทุกครั้งที่ commit เพิ่ม (เอกสารฉบับก่อนหน้าเขียน "42 commit · PR 2 ใบ"
> แล้วผิดทันทีที่ตัวมันเองถูก merge เข้าไป) ส่วนจุดที่เปลี่ยนวิธีทำงานเป็นตัวเลขที่ไม่มีวันเปลี่ยน
> ตัวเลขล่าสุดดูได้จาก `git rev-list --count HEAD` และหน้า Pull requests บน GitHub

ขัดกับแผนสัปดาห์ 2 ที่เขียนไว้เองว่าจะ "ตั้ง branching strategy" และขัดกับเกณฑ์
**Code & Collaboration (15 คะแนน)** ที่ต้องการ "Git/Issue/Branch/PR/Review ใช้จริง"

**ทำไมถึงเกิด:** ทำงานคนเดียว ไม่มีใครต้องรอรีวิว การแตก branch จึงรู้สึกเหมือนพิธีกรรมเปล่า ๆ
ระหว่างที่กำลังเร่งงาน — เป็นเหตุผลที่ฟังดูสมเหตุสมผลตอนนั้น แต่ผิดตรงที่ branch/PR
ไม่ได้มีไว้เพื่อ "รอคนอื่น" อย่างเดียว มันคือจุดที่บังคับให้หยุดสรุปว่าการเปลี่ยนแปลงนี้คืออะไร
และตรวจสอบมันยังไง ก่อนที่มันจะเข้าไปปนกับของเดิม

**ข้อจำกัดที่ต้องพูดให้ชัด — PR ส่วนใหญ่ยังไม่ใช่ "code review"**

**PR #1–#22 ทุกใบมี `reviews = 0`** ผู้เขียนกับผู้ merge เป็นคนเดียวกัน
สิ่งที่ได้จริงจากใบเหล่านั้นคือ **branch hygiene + CI gate + บันทึกเหตุผลของการเปลี่ยนแปลง**
ไม่ใช่การมีสายตาที่สองมาตรวจ · การนับว่า "มี PR แล้ว = ผ่านเกณฑ์ Review" จะเป็นการอ้างเกินจริง

**[PR #23](https://github.com/kit-sinlapasa/sme-inventory-system/pull/23) เป็นใบแรกที่มี
รีวิวจริง** — สมาชิกกลุ่มที่ไม่ใช่ผู้เขียนโค้ดตอบคำถามครบ 3 ข้อ **และไม่เห็นด้วย 2 ข้อ**
โดยข้อ *"อยากได้คน test เพิ่ม"* ถูกนำไปแก้จริง (ทดสอบเพิ่ม 3 คน n 4→7)
ส่วนข้อ *"ใช้ชื่อจริงแทนรหัส P"* ไม่รับ เพราะ repo เป็นสาธารณะและจะขัดกับ NFR-PRIV-01
ที่ระบบนี้บังคับใช้เอง — บันทึกทั้งที่รับและไม่รับไว้ใน [docs/06 §B5](06-Usability-Test-NFR-USE-01.md)

**ตั้งใจไม่ย้อนไปหารีวิวให้ PR #1–#22** — รีวิวที่มาหลัง merge ไม่ใช่หลักฐานว่ามีคนตรวจ
ก่อนขึ้น `main` มันเป็นแค่ลายเซ็นย้อนหลัง · สถิติที่ซื่อสัตย์คือ **1 ใบจาก 23 ใบที่มีรีวิวจริง**

**AI ไม่นับเป็น reviewer คนที่สอง** — AI เป็นคนเขียนโค้ดเกือบทั้งหมดในโครงงานนี้
ให้ AI รีวิวงานตัวเองไม่ใช่ independent review และตลอดโครงงานก็พิสูจน์แล้วหลายครั้งว่า
AI มองข้ามงานตัวเองได้จริง (ดู `02-AI-Usage-Log.md` หัวข้อ "สิ่งที่ AI ถูก Reject หรือแก้ไข" —
เช่น จัดกลุ่มเวลาด้วย UTC แทนเวลาไทยจนกราฟผิดวันโดยหน้าจอยังดูปกติ,
เขียน `.filter()` ต่อท้าย `.limit()` ที่พังเฉพาะ role เดียว, และเคลมใน RTM ว่า verify ครบ
ทั้งที่ยังไม่ได้กด 2 ปุ่ม) — บั๊กเหล่านี้ถูกจับได้เพราะ **รันจริงแล้ววัดผล** ไม่ใช่เพราะอ่านโค้ดซ้ำ

**สิ่งที่ได้จริงจากการเปลี่ยนมาใช้ PR แม้จะช้า:** การต้องเขียนคำอธิบาย PR บังคับให้เรียบเรียงว่า
"พิสูจน์ยังไงว่าถูก" ซึ่งใน PR #2 นำไปสู่การเอา test ใหม่ไปรันกับโค้ดเก่าเพื่อดูว่ามัน fail จริงไหม
แล้วพบว่า **test ตัวหนึ่งไม่ fail** เพราะดักฟัง engine ผิดตัว — ถ้า push ตรงเข้า main
เหมือน 38 ครั้งก่อนหน้า test ที่วัดอะไรไม่ได้เลยตัวนั้นก็คงเข้าไปอยู่ในระบบเรียบร้อย

**ถ้าทำใหม่:** ตั้ง branch protection บน `main` ตั้งแต่ commit แรกให้ push ตรงไม่ได้เลย
บังคับด้วยเครื่องมือ ไม่ใช่ด้วยความตั้งใจ — เพราะวินัยที่ต้องใช้ใจสู้ทุกครั้งจะแพ้ความเร่งเสมอ
และหาเพื่อนร่วมชั้น 1 คนสลับกันรีวิว PR ให้กัน**ตั้งแต่ใบแรก** เพื่อให้ส่วน Review มีของจริง
ตลอดเส้นทาง ไม่ใช่แค่ใบสุดท้ายอย่างที่เกิดขึ้นจริง

**ทำแล้วจริง (ช่วงท้ายโครงงาน):** เปิด branch protection บน `main` แล้ว — บังคับให้ทุกการเปลี่ยนแปลง
ผ่าน Pull Request, ต้องผ่าน CI ทั้ง 2 job ก่อน merge, branch ต้อง up-to-date กับ `main` ก่อน,
ห้าม force push และห้ามลบ branch · เปิด `enforce_admins` ด้วย เจ้าของ repo เองจึง push ตรงไม่ได้
พิสูจน์แล้วด้วยการลอง push ตรงจริง ได้ `remote rejected ... protected branch hook declined`

ตั้ง **required approving reviews = 0** โดยตั้งใจ ไม่ใช่ลืม — GitHub ไม่อนุญาตให้ approve PR ของตัวเอง
ถ้าตั้งเป็น 1 ในสภาพที่ทำงานคนเดียวจะ merge งานตัวเองไม่ได้เลย กฎชุดนี้จึงบังคับได้แค่
**"ห้าม push ตรง + CI ต้องผ่าน"** ไม่ได้บังคับว่ามีคนรีวิว — ซึ่งตรงกับที่บันทึกไว้ข้างบนว่า
ส่วน Review ยังไม่ถูกเติมเต็ม การตั้งค่านี้ไม่ได้ทำให้ช่องว่างนั้นหายไป

## 4. สิ่งที่จะปรับปรุงถ้าทำโปรเจกต์นี้ใหม่

1. **ยืนยัน scope และ timeline ให้นิ่งก่อนเริ่ม** — ปัญหาข้อ 2.1/2.2 ทั้งคู่แก้ได้ด้วยการใช้เวลาช่วง elicitation ให้ครบถ้วนกว่านี้ ก่อนเริ่มออกแบบ ไม่ใช่แก้ทีละ CR ระหว่างทาง
2. **ตั้ง isolated dev environment (venv/container) เป็นขั้นตอนแรกสุด** ไม่ใช่ทำทีหลัง — ป้องกันปัญหาข้อ 2.5 ได้ตั้งแต่ต้น
3. **เริ่มใช้ git branch + PR ตั้งแต่ commit แรก และ "บังคับด้วยเครื่องมือ ไม่ใช่ด้วยความตั้งใจ"** — ตั้ง branch protection บน `main` ให้ push ตรงไม่ได้เลยตั้งแต่วันแรก เพราะวินัยที่ต้องใช้ใจสู้ทุกครั้งจะแพ้ความเร่งเสมอ (โครงงานนี้พิสูจน์แล้ว: ตั้งใจไว้ในแผนสัปดาห์ 2 แต่จริง ๆ เริ่มใช้ PR ตอน commit ที่ 39 และเพิ่งตั้ง branch protection ช่วงท้ายสุด) · และหาเพื่อนร่วมชั้น 1 คนสลับกันรีวิว PR เพราะ PR ที่ไม่มีใครรีวิวยังไม่ใช่ code review
4. **ทดสอบ deploy configuration แบบ end-to-end ตั้งแต่ก่อน push จริง** (เช่น รัน `startCommand` เป๊ะตามที่เขียนใน `render.yaml` บนเครื่อง local ก่อน) แทนที่จะรอ deploy fail จริงแล้วค่อยไล่ debug ทีละรอบ
5. **แทรก usability test คู่ขนานกับการพัฒนา UI** แทนที่จะทิ้งไว้เป็นงาน "สัปดาห์สุดท้าย" ที่สุดท้ายอาจไม่มีเวลาทำจริง

## 5. บทสะท้อนเรื่องการทำงานร่วมกับ AI

โครงงานนี้ใช้ AI (Claude) ช่วยแทบทุกขั้นตอน ตั้งแต่ requirement elicitation ไปจนถึง security hardening — สิ่งที่ยืนยันได้จากบันทึกจริงใน `docs/02-AI-Usage-Log.md` คือ **AI มีประโยชน์ที่สุดตอนถูกบังคับให้ verify ตัวเอง** (รัน test จริง, เปิด browser จริง, เรียก API จริงผ่าน public internet) ไม่ใช่ตอนแค่เขียนโค้ดแล้วอธิบายว่าน่าจะถูก — บั๊กที่ร้ายแรงที่สุดที่พบทั้งหมด (deploy failure, debounce logic, seed script) ถูกจับได้เพราะมีขั้นตอน "รันจริงก่อนถือว่าเสร็จ" กำกับไว้เสมอ ไม่ใช่เพราะ AI เขียนโค้ดถูกตั้งแต่ครั้งแรก

ในทางกลับกัน AI ก็ทำผิดพลาดได้จริงเช่นกัน (ดูข้อ 2.5) และจุดที่ต้องเรียนรู้คือ **AI ที่ไม่มีสิทธิ์เข้าถึงระบบภายนอกโดยตรง (เช่น Render dashboard log ตอนแรก) จะเดาผิดได้ง่าย** — ต้องอาศัยมนุษย์เป็นสะพานส่งหลักฐานกลับมาเสมอ ไม่ใช่ปล่อยให้ AI ตัดสินใจจากข้อมูลที่ไม่ครบ

ข้อควรระวังสำหรับทีมก่อนส่งงานจริง: **AI Usage Log entry #4 และ #5 ยังเป็นจุดอ่อนที่สุด** เพราะทีม verify แบบ "โอเค"/"ทำเลย" แบบกว้าง ๆ ไม่ได้ทวนรายละเอียดทีละบรรทัดจริง — ทีมควรกลับไปอ่าน [01-Requirements-Package.md](01-Requirements-Package.md) อีกรอบก่อนส่งจริงตามที่บันทึกไว้แล้วในเอกสารนั้น
