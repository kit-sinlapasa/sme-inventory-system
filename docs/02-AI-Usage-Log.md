- **Entry #29 → #30:** AI สร้างธีมทั้งระบบจากภาพตัวอย่างที่ไม่เกี่ยวกับ Render ทั้งที่ทีมให้ URL จริงมาตั้งแต่ต้น — พอตรวจ `dashboard.render.com` ด้วย `getComputedStyle()` จริงพบว่าเป็นธีม**สว่าง** ไม่ใช่มืดอย่างที่ทำไป ต้องรื้อทำใหม่ทั้งหมด (**บทเรียน: มี URL ให้ตรวจได้ ต้องตรวจก่อนลงมือ ไม่ใช่เดาจากภาพ**)
- **Entry #42 (สองจุด — ทั้งคู่เป็นบั๊กที่ "โปรแกรมไม่ error และหน้าจอดูปกติ"):**
  1. **แผนแรกของ AI จะทำให้กราฟรายสัปดาห์ผิดวันโดยไม่มีอะไรฟ้อง** — ตั้งใจสุ่มเวลาขาย 9:00–20:00 น. แต่สร้างบนนาฬิกา UTC ซึ่งเท่ากับ 16:00–03:00 น. เวลาไทย ทำให้ยอดขายราว 1 ใน 3 ตกไปนับเป็นวันถัดไปตอน frontend เรนเดอร์ด้วย `th-TH` ผลคือกราฟ**ยังมีความต่างให้เห็น** (ผ่านการตรวจแบบ "ดูแล้วไม่แบน") แต่เป็นความต่างที่ผิดวัน — อันตรายกว่ากราฟที่เสียชัด ๆ แก้โดยสร้างเวลาในโซนไทยทั้งหมดและใช้ `AT TIME ZONE 'Asia/Bangkok'` ทุกจุดที่ truncate
  2. **เขียน `.filter()` ต่อท้าย `.limit()`** ใน `top-products` และ `pending-requests` — พังเฉพาะตอนพนักงานสาขาเปิดหน้า (Admin ใช้ได้ปกติเพราะไม่มี branch filter) เจอตอนรัน test จริงด้วยบัญชีสาขา ไม่ใช่ตอนกดดูหน้าจอ · ถึงจะเรียงลำดับได้ก็ยังผิดความหมายอยู่ดี เพราะจะได้ "10 อันดับของทุกสาขา แล้วค่อยตัดเหลือสาขาตัวเอง" แทนที่จะเป็น "10 อันดับของสาขาตัวเอง" — จึงเพิ่ม test 2 เคสที่จับเรื่องนี้โดยเฉพาะ
  3. **ตัวเลข 2 คู่บนหน้าจอเดียวกันไม่ตรงกัน** (พบตอน review รอบสุดท้าย จากการอ่านผลลัพธ์ที่ตัวเอง capture ไว้ก่อนหน้า): KPI ค้างสต็อก = 64 แต่แท่ง "180+" ที่อยู่ใต้มันเอง = 63 เพราะใช้นิยามอายุคนละแบบ · และ KPI ใกล้หมด = 92 แต่ตารางด้านล่างแสดงได้ไม่ถึง เพราะ KPI นับของที่หมดเกลี้ยงแล้วด้วยแต่ตารางแสดงไม่ได้ — รายละเอียดและวิธีแก้อยู่ใน CR-013 · **บทเรียน: การ verify ทีละส่วนว่า "ส่วนนี้ถูก" ไม่ได้แปลว่าตัวเลขที่อยู่ข้าง ๆ กันบนหน้าจอจะสอดคล้องกัน ต้องอ่านเทียบกันตรง ๆ ด้วย**
  4. **เขียนใน RTM ว่า "verify ครบทุก interaction" ทั้งที่ยังไม่ได้ทดสอบ 2 อัน** (คลิกแท่งกราฟ → modal, คลิกแถวตารางเสี่ยงของขาด → modal — อันหลังยังไม่เคยถูกกดเลยเพราะตอนทดสอบไปกดปุ่ม "ขอสั่งซื้อ" ซึ่ง `stopPropagation()` ไว้) · **การเคลมการตรวจสอบเกินจริงเสียคะแนนมากกว่าการมีฟีเจอร์ไม่ครบ** เพราะ rubric ให้คะแนนที่คุณภาพของหลักฐาน — แก้โดยกดจริงทั้งสองอัน (ได้ modal ถูกตัวทั้งคู่) แล้วเขียน RTM ใหม่ให้ระบุเป็นรายการว่าทดสอบอะไรไปบ้าง แทนคำว่า "ครบทุก"
  5. **เขียน test ที่วัดอะไรไม่ได้เลย** (entry #43) — test กัน N+1 ที่ไปดักฟัง database engine ผิดตัว จึงนับ query ของ fixture แทนของ API **จะผ่านตลอดไม่ว่า endpoint จะแย่แค่ไหน** · จับได้เพราะเอา test ไปรันกับโค้ดเก่าที่ยังมีบั๊กแล้วมันไม่ fail — **บทเรียน: test ที่ผ่านไม่ได้แปลว่าโค้ดถูก ต้องพิสูจน์ก่อนว่า test จะ fail เมื่อโค้ดผิดจริง**
  6. **เขียนเครื่องมือวัดที่บอกว่าผ่านหมดทั้งที่มีข้อที่ตก** (entry #45) — สคริปต์วัด usability สลับลำดับพารามิเตอร์ ทำให้ชื่อการทดสอบถูกใช้เป็นเงื่อนไข ซึ่ง truthy เสมอ → **10/10 ผ่าน ทั้งที่จริง 8/10** · จับได้เพราะสังเกตว่าชื่อการทดสอบพิมพ์ออกมาเป็น `true`/`false` — **บทเรียนเดียวกับข้อ 5 ในรูปแบบใหม่: เครื่องมือที่รายงานว่าผ่านทุกข้อ ควรถูกสงสัยก่อนเชื่อ**
  7. **อ้างเลข entry ผิดในเอกสารของตัวเอง** (entry #46) — เขียนว่าความผิดพลาดเรื่องธีมคือ entry #10 ทั้งที่ #10 เป็นเรื่องสร้าง GitHub repo · ของจริงคือ **#29 (ทำผิด) → #30 (แก้)** · ที่แย่กว่านั้นคือ**เลขนี้ผิดมาตั้งแต่รอบก่อนแล้ว**และหลุดเข้าเอกสารไป จับได้เพราะไล่เช็คทุกเลขที่อ้างกับตารางจริงก่อน commit — **การอ้างอิงที่ตรวจไม่ได้ ทำลายความน่าเชื่อถือของ log ทั้งฉบับ มากกว่าการไม่อ้างเลย**
